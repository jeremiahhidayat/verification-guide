# 9.4 Levels and Flows Beyond Block-Level RTL Simulation

## Block, subsystem, SoC

| Level | DUT | Stimulus | Checking | Typical speed | What it finds |
|---|---|---|---|---|---|
| **Block / IP** | One module or IP (FIFO, DMA, PCIe controller) | Active UVM agents on every interface; constrained-random; formal | Scoreboards with full models; assertions; coverage closure | 10k to 100k cycles/s | Functional bugs in the block; spec ambiguities |
| **Subsystem** | Several blocks plus interconnect (a CPU cluster, a video pipeline) | Active agents at the boundary; block agents passive; C tests on an embedded CPU model | Block scoreboards still active; subsystem end-to-end checks; address-map checks | 1k to 10k cycles/s | Integration: connectivity, address decode, arbitration interactions, clock/reset domains |
| **SoC / top** | The whole chip RTL | Real boot ROM and firmware on the real CPU model; bus VIP on external ports; formal connectivity | Firmware self-checks; passive agents; assertions; register/connectivity formal | 10s to 1k cycles/s | Boot, software-visible behavior, IO connectivity, power sequencing, interrupts |
| **Emulation** (Palladium, ZeBu, Veloce) | Synthesizable RTL (plus transactors) | Real software stacks, OS boot, traffic from virtual/real hosts | Software; transactor-based checkers; limited assertions | 1 to 10 MHz | Long scenarios, performance, software/hardware bugs; DV coverage is limited |
| **FPGA prototyping** | RTL mapped to FPGAs | Real interfaces, real software | Software; logic analyzers | 10 to 100 MHz | Software development, system validation; poor observability |
| **Gate-level simulation (GLS)** | Post-synthesis / post-layout netlist, optionally with SDF timing | Subset of block/SoC tests | Same checkers; X-checks; timing checks | 10 to 100 cycles/s | Synthesis/DFT/ECO mismatches, reset and X issues, timing violations on critical paths, power intent bugs |

The principle: verify each thing at the lowest level where it is controllable and observable, and
use higher levels to verify *integration*, not to re-verify block function. Reuse (passive agents,
shared scoreboards, shared sequences) is what keeps this economical.

## Hardware/software co-verification

At subsystem and SoC level, stimulus is often *software*: C tests compiled for the embedded CPU,
loaded into memory models, executed by the CPU RTL (or a fast ISS model swapped in for speed).
Verification engineers write or co-write these tests, provide the "test harness" (a small runtime:
printf via a UART or a magic register, pass/fail signaling, interrupt handlers), and connect the
UVM environment so that software-triggered activity is checked by the same scoreboards. DPI-C
(9.6) bridges SV and C when the test runs natively.

## Low-power verification (UPF/CPF)

Power intent (domains, switches, isolation, retention, level shifters) is specified in UPF, not
RTL. Power-aware simulation (`-pa`, `-upf`) applies it: powered-down domains corrupt their state,
isolation cells clamp outputs, retention registers keep values. What you verify: every domain's
power-up/down sequence, isolation is enabled before power-down and released after power-up,
retention saves/restores correctly, no X escapes a domain boundary, the power state machine
(PMU) FSM is correct. Tests: all transitions of the power state table, with traffic active during
transitions. Assertions on isolation/retention control signal ordering are standard. Static
checks (UPF lint) come first.

## Clock domain crossing (CDC) and reset domain crossing (RDC)

RTL simulation is zero-delay and cannot show metastability. CDC is verified by:

1. **Structural CDC tools** (Questa CDC, SpyGlass CDC, Conformal CDC): find every crossing;
   classify (single-bit synchronizer, handshake, FIFO, gray-coded pointer, mux-sync); report
   missing/incorrect synchronizers, convergence/reconvergence, glitch-prone combinational logic
   before a synchronizer.
2. **Protocol assertions** generated by the CDC tool or written by hand (chapter 3 cookbook): data
   stable while the request is in flight, gray code changes one bit per cycle, mux select stable.
   Run in simulation and formal.
3. **Metastability injection** in simulation (tool option or synchronizer models with random extra
   delay) to expose logic that assumes a fixed synchronizer latency.

RDC: asynchronous resets crossing into other domains cause the same class of bugs (a reset
asserting in domain A while B is mid-transaction). Same tool category; the fix is reset
synchronizers and ordering assertions.

## Lint and static checks

Before any simulation: RTL lint (naming, width, unused, latch, multi-driver, synthesis-unsafe
constructs), CDC/RDC, UPF lint, DFT rules. Verification owns the "lint clean" gate on many teams
because a lint failure often indicates a bug the testbench will otherwise spend a week finding
(implicit net truncation, 1.6 G2).

## DFT and test-mode verification

Scan chains, BIST, boundary scan (JTAG), and test modes are inserted logic that must be verified:
scan shift/capture in GLS with ATPG patterns, BIST self-test sequences, and, importantly, that
*functional* mode is unaffected by DFT insertion (SEC or regression on the DFT-inserted netlist).
Verification usually owns the JTAG/TAP controller environment and the "test mode disables
everything correctly" tests.

## Gate-level simulation in practice

GLS is slow, X-pessimistic, and painful, so it is used surgically: a boot test, a reset test per
domain, a handful of P1 functional tests, DFT patterns, and low-power sequences, on the final
netlist with SDF (`-sdf max/min`). Typical findings: uninitialized flops that RTL sim
(X-optimistic in `if`) hid, synthesis pragmas that removed logic, clock-gating bugs, timing
violations on multicycle/false paths that were mis-constrained. Prepare for GLS from day one by
keeping the testbench free of hierarchical references into the DUT (names change in the netlist)
and by binding assertions through interfaces rather than internal signals where possible.

## Post-silicon

Silicon arrives; tests run on real chips. Verification engineers contribute: the test plan mapping
(which pre-silicon tests correspond to which bring-up tests), debug support (correlating a silicon
failure back to an RTL scenario, reproducing it in emulation/simulation), and the escape analysis
(9.3's post-mortem). Every silicon bug becomes a regression test for the next generation.

## Interview angle

- "What changes when you move from block to subsystem to SoC?" Active to passive agents; software
  as stimulus; speed; what each level is for.
- "What is GLS for, and why not do everything there?" Netlist-specific bugs; speed and observability.
- "How do you verify CDC?" Structural tool, protocol assertions, metastability injection; RTL sim
  alone cannot.
- "What does low-power verification involve?" UPF, power-aware sim, isolation/retention/PMU FSM
  checks.
- "Emulation vs simulation?" Speed vs observability/debug; software-driven scenarios.

## Mentor's notes

- Design your block environment for the day it goes passive. It is the difference between a
  subsystem bring-up that takes a week and one that takes a quarter.
- Volunteer for GLS once. It is miserable, and afterward you will write RTL-level checks that
  catch the same bugs a month earlier.
